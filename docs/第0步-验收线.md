### ② 黄金参考

同一份 JHYY 源码：

- **A 路**（第 0 步）：JHYY → C → clang → ELF → `.bin`
- **B 路**（将来）：JHYY → ARM 机器码 → ELF → `.bin`

两条路的产物**行为一致**，且**逐层可定位**：
`.s` / `.o` / ELF / `.map` / 最终 `.bin` **全部留存**，不只存 `.bin` ⇒
B 阶段对拍时能回答"从哪一层开始不一致"。

### ③ 实机可跑

A 路产出的 `.bin` **真的在 Brain 上转了电机**（不是"应该能跑"）。

## 2. 拆解

### Day 0 — 先别写 emitter（✅ 已完成）

**做法**：手工写一个 C 文件，**零 JHYY 变量**，用实测过的工具链纯手工走通
`源码 → ELF → 带签名 bin → program.bin`。

**为什么这样切**：VEX 侧的一切在 emitter 存在之前都是未知数。
不先把它实测掉，B 阶段一旦烧不亮，你分不清是签名放错段、栈没设、`.bss` 没清，
还是寄存器分配器把 r0 弄丢了。

**产出**：

| 产物 | 位置 |
|---|---|
| 手写 C 探针 | [`spike/day0-c/src/main.c`](../spike/day0-c/src/main.c) |
| 待烧录产物 | `spike/day0-c/program.bin`（2756 B） |
| 实测事实 | [`00-事实基线.md`](00-事实基线.md) 全文 |

**已实测的关键结论**（详见事实基线）：

- 产物格式**不需要额外转换器** —— SDK 的 `objcopy` 路径直出最终格式；
  头 32 字节 `XVX5` + 版本 1，入口 `0x03800020`。
- **启动链完全闭合**：`.boot:vexStartup` → 清 bss/sbss → stdlib 版本校验 →
  newlib impure data → `__libc_init_array` → `vexMain` → `__libc_fini_array`。
- **并发模型**：用户的 `main` 是 `vexTaskAdd(main, 2, "MAIN")` 注册的 **task**。
- **ABI 锁定 softfp**（我们与 `libv5rt.a` 双向一致）。
- **指令集是 ARM 态 4 字节定长** ⇒ 后端不必做 Thumb-2 变长编码。
- **没有隐藏的全局初始化**（`vexcodeInit` 是工程自带的空壳）。
- 内存预算：堆 1 MB / 栈 14 KB / 代码段 1.6 KB。

### Day 1–2 — emitter 发 **C**，不发 C++

**理由**：绑定层是 `extern "C"`，输出 C 就没有 name mangling，
`extern fn` 一一对应，少一整类问题。

**最小子集**（够用即可，不许扩）：

常量 · `let` · 算术 · `if` / `while` · 函数调用 · `extern fn` 声明 ·
字符串字面量 · struct 布局

**最小绑定面**（不许一上来 400 个 API）：先只绑

```
vexDeviceGetByIndex / vexDeviceMotorVelocitySet / vexDelay / vexDisplayPrintf
```

外加一个屏显。**其余等真的需要时再加。**

### Day 3 — 对拍与规格书收口

- A 路产物 vs 7262A 现有 C++ 工程的**行为对照**（同一段逻辑两种写法）。
- 把 Day 0 遗留的待测项（tick 频率、屏显语义）补齐。
- 规格书定稿。

## 3. 🔒 写死条款（不可协商）

> **这一节的存在是为了防一件具体的事：spike 变成舍不得拆的项目。**
>
> 参照物：vexide 的 `pros-rs` 阶段做了 7500 行、815 commits、发布到 v0.9.0，
> 最后推倒重来时**7500 行实现全扔了**，只留下 API 形状与设计判断。
> 他们的 spike 做成了产品，于是有了沉没成本。
>
> **我们的第 0 步从第一天就明确：产出是知识，不是代码。**

### 3.1 emitter 是**探针**，不是产品

- emitter 代码**不追求**通用、完整、可维护。
- 遇到"这个特性 JHYY 现在不支持" ⇒ **记进规格书的问题清单，不在 emitter 里绕过**。
  （例：`fn(...)` 类型位置不被认 ⇒ 记下来，别自己造个函数指针类型硬塞。）

### 3.2 进入 B 阶段的条件

同时满足才允许动 B：

- [ ] 规格书八项全部有实测值（tick 频率除外，允许"实机已测但暂缺"）
- [ ] A 路 `.bin` 已在 Brain 上转过电机
- [ ] `.s` / `.o` / ELF / `.map` / `.bin` 五层产物齐全且留存
- [ ] ABI 决定（softfp）在 A 路与 B 路**写在同一处**且已被门检查

### 3.3 A 路的产物**不是废品**，但也不是遗产

- **是**：B 阶段的黄金参考 —— 同一份源码两条路，行为必须一致。
- **是**：规格书的可执行副本。
- **不是**：未来要长期维护的第二套后端。
  ⇒ emitter 代码在 B 阶段**只保留最小可用状态**（够跑对拍用例即可），
  不得反向长成"JHYY 的 C 后端"。

### 3.4 一条硬边界

**JHYY 主仓（JiHuiYiYou）的改动，一律先在本仓（jhyy-for-vex）做实验、拿到实测，
再回主仓落地，并单独评审。** 本仓不直接改主仓。

---

## 4. 明确不做

| 不做 | 理由 |
|---|---|
| 一开始绑全部 VEX API | 400+ API 会让 emitter 变成产品（见 § 3.1） |
| 在 emitter 里造 JHYY 没有的语言特性 | 那属于主仓的编译器演进，不是第 0 步 |
| 直接改主仓加 C 后端 | 见 § 3.4；先在本仓实测 |
| 碰赛季代码 | 本项目定位：**纯技术探索**，不动 7262A 的比赛代码 |
| 实现 Thumb-2 变长编码 | 实测：目标是 ARM 态 4 字节定长 |

## 5. 第 0 步的副产物：桌面侧

**不单列成一个阶段**（与第 0 步并行、零成本）：

- 同一份 JHYY 源码在 **host** 上跑逻辑、在 **Brain** 上跑 `.bin` ⇒ 双保险。
- 参照 vexide 的做法（`vex-sdk-mock` 让机器码代码在 PC 上 `run` + `test`）。
- 与 `VEXAutoViz` 的关系（它现在用 regex 解析 `Auto.cpp`）：
  若 JHYY 侧能 emit 一个 JSON 轨迹事件流，可视化器改吃 JSON 而非解析 C++ 文本 ——
  **这是独立议题**，不作为第 0 步的验收项。
