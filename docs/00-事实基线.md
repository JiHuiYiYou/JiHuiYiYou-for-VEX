## 3. 产物格式（实测，最关键的一条）

`.bin` 就是 `arm-none-eabi-objcopy -O binary` 的裸镜像，**SDK 路径直接产出最终格式** ——
**不需要** cargo-v5 那类额外格式转换器。

### 3.1 头部 32 字节 = `.boot_data` 段

来自 `libv5rt.a(v5_startup.c.obj)`，链接后落在 `0x03800000`：

```
偏移  内容            含义
+0x00 "XVX5"         魔数（4 字节 ASCII）
+0x04 00000000
+0x08 01000000       版本号 = 1
+0x0C … 0x1F  全 0   （共 28 字节）
```

实测两处一致：`day0c.bin`（手写 C 探针）与 `1AWP.bin`（你的赛季工程）头部 32 字节完全相同。

### 3.2 入口

- `.boot_data` 之后 **立即是入口**：`0x03800020` = `vexStartup`。
- ELF header 的 `Entry point address` = **0x03800020**。

### 3.3 `vexCodeSig` 是 weak object

`nm` 显示 `V vexCodeSig`（weak）⇒ **可被同名强符号覆盖**（将来若要自定义签名/版本，不必改 SDK）。

### 3.4 SD 卡

## 4. 目标平台

| 项 | 实测值 | 证据 |
|---|---|---|
| ELF | ELF32 / little endian / **Machine: ARM** | `readelf -h` |
| EABI flags | `0x5000202, Version5 EABI, **soft-float ABI**` | `readelf -h` |
| 入口 | `0x03800020` | `readelf -h` |
| 指令集 | **ARM 态，4 字节定长** | 入口处 `e59f00a0` 是 ARM 态 LDR literal（Thumb-2 会是 `f8df`） |
| CPU | Xilinx Zynq（Cortex-A9 + FPGA） | `lscript.ld` 里 `ps7_ddr_0_S_AXI_BASEADDR = 0x03800000` |
| 浮点硬件 | 有 VFPv3 + NEON | `-mfpu=neon` |
| 浮点 ABI | **softfp**（base standard variant） | 见 § 6 |

> ⇒ **后端不必做 Thumb-2 变长编码**（ARM 态定长 4 字节）。
> ⚠️ 但 `-target thumbv7-none-eabi` 仍在 flags 里 ⇒ clang 允许 Thumb，但 SDK 实际
> 由 `.boot` 段与入口代码走 ARM 态。**B 阶段按 ARM 态发指令**。

## 5. 启动链（反汇编 + 重定位双重确认）

```
.boot : vexStartup            ← 入口 0x03800020（SDK 提供，172 B）
  ├ 清 .bss   (__bss_start → __bss_end，4 字节粒度 strlt)
  ├ 清 .sbss  (__sbss_start → __sbss_end)
  ├ vexStdlibVersionVerify() → 为 0 则比 vexStdlibVersion() vs vexStdlibVersionLinked()
  │                            → vexStdlibMismatchError() → 打印 "Stop VEX code" 并退出
  ├ vexSystemStdlibImpureDataAddr()：非 0 且非 -1 →
  │    vexSystemStdlibImpureDataSize() 必须 == 0x428(1064)，否则跳过
  │    → 把 newlib 的 _impure_ptr 指向它并清零 1064 字节
  │    （否则调 vexSystemSaveUserData()）
  ├ __libc_init_array()
  ├ vexMain()          ← SDK 的壳
  └ __libc_fini_array() → return 0

.text : vexMain               ← SDK 提供，176 B
  ├ vexDebug("Start VEX code\n")
  ├ vexPrivateApiEnable(__vex_critical_section)
  ├ vexTaskAdd(main, priority=2, "MAIN")     ← ★ 你的 main 在这里被注册成 task
  ├ vexTaskGetTaskIndex("MAIN") + vexTaskCompletionIdSet()
  ├ vexTasksDump()
  └ 循环：*appRunning ? vexTasksRun() : (vexTaskStopAll() + "Stop VEX code\n"
                                          + 500ms 超时轮询 vexSystemTimeGet
                                          + vexSystemExitRequest())
```

字符串表（`.rodata.str1.1`，46 B）：`"Start VEX code\n"` `"MAIN"` `"Stop VEX code\n"` `"_exit %d\n"`。

## 6. 并发模型（实测）

**用户的 `main` 不是主线程**，而是被 `vexTaskAdd(main, priority=2, "MAIN")` 注册进
VEXos 固件调度器的**一个 task**。

⇒ `wait()` / `vexDelay()` 是**让出时间片**，不是"省 CPU"的可选项 —— 不让出会顶掉别的 task。
⇒ B 阶段 JHYY 的 `wait` 有原生对应物（`vexTaskSleep` / `vexTaskYield` / `vexTasksRun`）。

## 7. ABI 决定（**锁定**）

**决定：softfp（ARM base standard variant）。**

- 我们的 ELF 与 `libv5rt.a` **都没有 `Tag_ABI_VFP_args` 标签** ⇒ 按 ARM ABI，缺省即 base
  standard variant（浮点实参走核心寄存器 r0–r3，浮点返回走 r0/r1）。
- `readelf -h` 直接把我们的产物标成 **`soft-float ABI`**。
- 与 SDK flags `-mfloat-abi=softfp` 自洽。
- PROS 的 `-mfloat-abi=hard -mfpu=neon-fp16` 之所以不同，是因为它链的是**自己的**
  `libv5rts.a` ⇒ 印证「**链哪份库就认哪份 ABI**」。

> ⚠️ **第 0 步与 B 阶段必须锁同一个决定**，否则两条路对拍时差异会混进 ABI，黄金参考就废了。
> 这条与 JHYY 现有的 `amd64_win` / `amd64_sysv` 是同族问题（整数与浮点 bank 规则相反）⇒
> **是接口扩展，不是重写。**

### 8.1 device 模型与 struct 布局（实测）

**device 模型**

`V5_DeviceT = struct _V5_Device *`（**不透明指针**，实测 `sizeof` = **4 B**）⇒ JHYY 侧映射 `*u8`。
**C API 用设备句柄，不是端口号** —— `vexDeviceGetByIndex(index)` 才能拿到句柄。

> ⚠️ **实机实测：句柄非 NULL ≠ 设备在位**（§ 13.1）
> `vexDeviceGetByIndex(0..3)` **四个口全部返回非 NULL**（本轮只有 PORT1 插了电机），
> 而只有 PORT1 那个口真的能读写位置/速度。
> ⇒ **不能用 `handle != NULL` 判断"这个口有没有插东西"**。
> （VEXcode 的 Devices 面板另有其判据；C API 这层**没测出**可靠的"在位"判据 —— 仍待测。）

**struct 布局**（实测，脚本 `scripts/measure-abi.sh`，源 [`spike/day0-abi/abi_probe.c`](../spike/day0-abi/abi_probe.c)）

| 类型 | sizeof | alignof | packed? |
|---|---|---|---|
| `V5_DeviceT` | 4 | 4 | — （指针） |
| `V5_DeviceMotorPid` | **12** | **1** | ✅ `__attribute__((__packed__))` |
| `V5_DeviceVisionRgb` | **4** | **1** | ✅ packed |
| `V5_TouchStatus` | **16** | 4 | ❌ 无 packed ⇒ 有 padding |

字段偏移（实测）：

- `V5_DeviceMotorPid`：`kf`0 `kp`1 `ki`2 `kd`3 `filter`4 `pad1`5 **`limit`6** `threshold`8 `loopspeed`9 `pad2`10
  ⇒ `limit` 是 `uint16_t` 却落在**偏移 6**（不是 8）—— 这就是 packed 的证据。
- `V5_TouchStatus`：`lastEvent`0 **`lastXpos`2** `lastYpos`4 **`pressCount`8** `releaseCount`12
  ⇒ 对齐到 4，**不是**所有 SDK struct 都 packed。

**按值传 / 按值返回 struct —— C API 里只有一个类型**

全量扫描 `v5_api.h` + `v5_apiuser.h`（两个纯 C 头文件）的**所有**函数声明：

| 方向 | 类型 | 函数 |
|---|---|---|
| 按值传参 | `V5_DeviceVisionRgb` | `vexDeviceVisionWhiteBalanceSet` / `vexDeviceVisionLedColorSet` / `vexVisionWhiteBalanceSet` / `vexVisionLedColorSet` |
| 按值返回 | `V5_DeviceVisionRgb` | `vexDeviceVisionWhiteBalanceGet` / `vexDeviceVisionLedColorGet` / `vexVisionWhiteBalanceGet` / `vexVisionLedColorGet` |

**其余 struct 一律指针传递**（`V5_DeviceMotorPid *` / `V5_TouchStatus *` / `v5_image *` …）。

**实测的传递约定**（调用方与 SDK stub 两侧对上了）

| 场景 | 约定 | 证据 |
|---|---|---|
| ≤4 B 的 struct 按值传参 | **一个核心寄存器**（第 2 个实参 ⇒ `r1`），4 字节**小端**塞进一个字 | 调用方 `movw/movt r1`（`0x44332211` ⇒ red=0x11…brightness=0x44）；SDK stub `v5_apijump.c.obj` 里 `str r1,[sp,#4]` … `ldr r1,[sp,#4]` |
| ≤4 B 的 struct 按值返回 | **`r0`** | SDK stub 把固件返回的字按字节拆回 `r0` |
| 1 字节 enum 按值传参 | `ldrb` 读出后**零扩展**到 32 位寄存器 | 调用点 `e5d11000 ldrb r1,[r1]` |

> ⚠️ **JHYY 侧现在还不能直接绑这些 struct**：
> JHYY ABI v4.0.0 § 6 FFI 明确「**不支持 struct / enum 按值跨 FFI 边界**」，
> 且「`extern fn` 的参数 / 返回类型**不做编译期限制** —— 声明 struct 参数能编译通过，
> 但实际按地址传，与 C ABI 不符（**静默不符，无报错**）」。
> ⇒ **最小绑定面里不出现任何按值 struct 的函数**（本来也用不上）。
> ⇒ B 阶段若要支持，是个**接口扩展**（按验收线 § 3.4 的旁路口径：本仓自己养，不回灌主仓），
> 不是 emitter 能绕过的事。

> ⚠️ **指针宽度**：JHYY ABI v4.0.0 § 9 把「指针宽度（64 位）」列为**锁定**项，
> 且四个目标（`amd64_win` / `amd64_win_freestanding` / `amd64_sysv` / `amd64_sysv_freestanding`）
> **全是 amd64** ⇒ **JHYY 现在没有 ARM 目标**，指针是 8 字节。
> 而 VEX 的 `V5_DeviceT` 是 **4 字节**。
> ⇒ ARM 目标必须先把指针宽度定成 4，否则**连 `extern fn` 都对不上**。
> 这是 B 阶段的第一块硬骨头，记在这里，别到了 B 阶段才发现。
>
> 📌 **只卡 B 路（直出机器码），不卡 C 路**（2026-11-10 澄清）：
> **C 路（Day 1–2）完全不受影响** —— emitter 发的是 **C 类型**，
> 指针多宽由 **clang 的 `-target thumbv7`** 决定（自然就是 4 字节），
> **不需要动 JHYY 的 ABI**。
> （代价是：JHYY 语义说"指针 64 位"、VEX 上是 32 位 ⇒ 依赖 64 位指针语义的 JHYY
> 程序在 VEX 上行为不同 ⇒ 这是**已知偏差**，要写进 B 阶段的规格，不是阻塞。）
>
> 📌 **它在编译器里住在哪**（核查主仓 `be6d37b7`）：
> `compiler/src0/ir.jhyy` 的 `qbe_type_of()` 与 `compiler/src0/types.jhyy` 的 `size_of()`
> —— **两处都在共享层** ⇒ 若要把 VEX 做成"编译器里的后端"，这两处要动 ⇒ 详见验收线 § 3.4.3。
>
> ✅ **但 B 路原型绕开了它**（2026-11-10 实测走通）：B 路先在本仓做成 **assembler emitter**
> （`spike/route-b`：JHYY → AST → **ARM 汇编** → clang → `.bin`）⇒
> **寄存器与宽度由 emitter 自己决定**，压根不经过那两处共享层 ⇒
> **原型阶段完全不用 patch 编译器** ⇒「要不要给主仓加后端」这个决定**可以推迟**。

规则（JHYY ABI v4.0.0 § 6 FFI / § 3.6 名称修饰）：

- `extern fn` **只声明**，链接期由 `ld` 解析；符号**原样发射，不加修饰**。
- FFI 支持的实参/返回类型：**基础类型、`*T`、`bool`**。
  **不支持**：struct / enum **按值**跨边界、**变参**、回调函数。
- ⚠️ `extern fn` 的参数 / 返回类型**不做编译期检查** ——
  声明一个 struct 参数**能编译通过**，但实际按地址传，与 C ABI 不符（**静默不符**）。
  ⇒ 绑定面清单必须人工核对，**别让编译器兜底**。
- 设备句柄 `V5_DeviceT` 在 C 里是 4 字节指针，JHYY 侧映射 `*u8`
  （⚠️ 前提是 ARM 目标把指针宽度定成 4 —— 见 § 8.1 末尾）。

#### 9.2.1 ★ 表里必须带**精确 C 原型**，不能只写 JHYY 侧签名（实测 2026-11-10）

先只按「JHYY 侧签名」发原型（`extern char *vexDeviceGetByIndex(uint32_t);`），
在真实 VEX 构建环境里 **clang 报 4 处 `conflicting types`**：

```
src/main.c:8:15: error: conflicting types for 'vexDeviceGetByIndex'
extern char * vexDeviceGetByIndex(uint32_t index);
... v5_api.h:71: V5_DeviceT vexDeviceGetByIndex( uint32_t index );
src/main.c:9:13: error: conflicting types for 'vexDeviceMotorGearingSet'
extern void vexDeviceMotorGearingSet(char *dev, int32_t gear);
... v5_api.h:154: void vexDeviceMotorGearingSet( V5_DeviceT device, V5MotorGearset value );
```

⇒ 三个原因，各对应一个具体差异：

| 差异 | 例子 | 后果 |
|---|---|---|
| **指针类型** | `char *` vs `V5_DeviceT`（= `struct _V5_Device *`） | `conflicting types` |
| **enum 类型** | `int32_t` vs `V5MotorGearset`（**1 字节**） | `conflicting types` |
| **const** | `char *` vs `const char *` | `conflicting types` |

⇒ **绑定面表记的是 SDK 的精确原型** ⇒ 生成的 C **逐字**发它 ⇒
`v5.h` / `jhyy_vex.h` 会校验它 ⇒ **C 编译器就是绑定面 ABI 的检查器** ✔

#### 9.2.2 enum 的序号表与 ABI 结论（实测 2026-11-10）

JHYY **没有 enum** ⇒ enum 型的实参只能传**序号**：

| enum 类型 | 序号 → 成员 |
|---|---|
| `V5MotorGearset` | 0=`kMotorGearSet_36` / 1=`kMotorGearSet_18` / 2=`kMotorGearSet_06` |
| `V5MotorBrakeMode` | 0=`kV5MotorBrakeModeCoast` / 1=`kV5MotorBrakeModeBrake` / 2=`kV5MotorBrakeModeHold` |
| `V5MotorEncoderUnits` | 0=`kMotorEncoderDegrees` / 1=`kMotorEncoderRotations` / 2=`kMotorEncoderCounts` |

**实参**（AAPCS：小于 4 字节的实参放在 r0–r3 的**低字节**，高位未定义）：

> 我们**总是传零扩展的 32 位值** ⇒
> ① callee 按 1 字节读（`-fshort-enums`）→ 读到低字节 ✔
> ② callee 按 4 字节读（没开 `-fshort-enums`）→ 读到整个字 ✔
> **两种情况都对** ⇒ 这就是 enum 敢**直接绑**的前提。

**返回值**（1 字节 enum 返回时**只有低字节有定义**）：

> ⇒ **B 路必须 `and r0, r0, #0xff`**（实测产物里就有这条指令）；
> A 路由 clang 负责（它知道 enum 的宽度）。
> ⚠️ 反过来不成立：**不能**因为「callee 可能按 4 字节读」就不掩码 ——
> 那时掩码也安全（我们的 enum 值都 ≤ 2），但**必须**掩（callee 按 1 字节读时不掩就是错的）。

### 9.3 入口符号必须是 `main`（实测）

SDK 的 `vexMain`（`libv5rt.a(v5_startup.c.obj)`）用 **`R_ARM_ABS32 main`** 取用户 main
的地址，再交给 `vexTaskAdd(main, 2, "MAIN")` 注册成一个 task。

⇒ **B 路 JHYY 必须发射一个不带修饰的 `main` 符号**，`extern fn` 原样发射正好满足。

> 对照：JHYY 的 **hosted** 程序入口是 `main_jhyy`（语言规范 § 1.1）；
> freestanding / 嵌入式目标**由用户自带 entry 符号**（ABI § 17.6）——
> 在 VEX 上，那个符号**就叫 `main`**，由 SDK 的 `vexMain` 来取。
> ⇒ B 阶段的 ARM 目标要么发射 `main`，要么发射 `main` 的别名，**不能**沿用 `main_jhyy`。

### 9.4 变参 ⇒ 必须有非变参封装（**两路共用的同一个符号**）

VEX 的屏显 API **全是变参**：`vexDisplayPrintf(x, y, opaque, fmt, ...)` /
`vexDisplayStringAt(x, y, fmt, ...)` / `vexDisplayVPrintf(..., va_list)` 等。
JHYY **不支持变参调用**（ABI v4.0.0 § 6 FFI）。

⇒ 第 0 步探针里已经加了**绑定面本身**的一部分：

| 符号 | 签名 | 位置 |
|---|---|---|

### 9.5 场控状态的**位含义**（静态实测 2026-11-09 —— 不需要硬件）

`vexCompetitionStatus()` 返回一个位掩码，但 SDK 头文件**没写各位的含义**。
反汇编 `libv5rt.a(vex_competition.cpp.obj)` 的 `vex::competition` 五个判定函数
（重定位为准）⇒ 位含义**直接可读**：

| SDK 函数 | 指令 | 等价于 |
|---|---|---|
| `isEnabled()` | `and #1` → `eor #1` | **bit0 == 0** |
| `isDriverControl()` | `eor #2` → `ubfx #1,#1` | **bit1 == 0** |
| `isAutonomous()` | 调 `isDriverControl()` → `eor #1` | **= !isDriverControl()** |
| `isCompetitionSwitch()` | `and #12` → `sub #4` → `clz`/`lsr #5` | **(status & 0xC) == 4**（bit2 置、bit3 清） |
| `isFieldControl()` | `ubfx #3,#1` | **bit3 != 0** |

⇒ **`vexCompetitionStatus()` 的位含义（SDK 自己的口径）**：

| 位 | 含义 |
|---|---|
| bit0 | 置上 = **未启用**（`isEnabled()` 取反） |
| bit1 | 置上 = **不在 driver control**（`isDriverControl()` 取反） |
| bit2 | 置上 = **competition switch 插着**（且 bit3 清） |
| bit3 | 置上 = **field control system 插着** |

> ⇒ **JHYY 侧只需要 `extern fn vexCompetitionStatus() -> u32;`**，
> 位含义自己按上表判 —— **不需要 C++ 的 `vex::competition` 类** ✓
> （那正是绑定面要避开的一层，见 § 8）。
>
> ⇒ 所以 § 13 里那条"competition switch 插没插"**不用问人**：
> `controller.status`（§ 8.2）已经说明插的是控制器，
> `vexCompetitionStatus()` 的原值由程序记进日志，位含义在上表 ⇒ 闭环。
>
> ⚠️ **什么还没测**：插上 competition switch 之后 `vexCompetitionStatus()` 的原值
> 到底变不变（那是**固件行为**，静态测不出来）——
> 手边有那个开关的话，**拔掉控制器插上它再跑一次**，日志会追加一段，
> 两个 `M5.cstat` 一比就知道。没插就留「待测」。
>
> ✅ **实机读到的原值（§ 13.1）**：`vexCompetitionStatus()` = **0x0**
> ⇒ 按上表：`enabled = 1`、`driver control = 1`、
> **competition switch 未插**、**field control 未插**。
> （本轮插的是控制器，`controller.status=1` = USB tethered ✔）

### 9.7 电机的**速度与位置单位**（实测 2026-11-09 —— 这是最容易搞错的一条）

| 量 | 单位 | 证据（§ 13.1） |
|---|---|---|
| `vexDeviceMotorVelocitySet/Get` | **RPM（输出轴每分钟转数）** | 设 50 → 实际读回 48.4~51.1；转 1 秒位置 **270.4°** |
| `vexDeviceMotorActualVelocityGet` | 同上（**RPM**） | 同一次测量里 = 48.4~51.1 |
| `vexDeviceMotorPositionGet` | **度（输出轴）** | 1 秒 = 270.4°，且 `kMotorEncoderDegrees` 下就是度 |
| `vexDeviceMotorDirectionGet` | **±1**（符号，不是角度） | +50 → `1`；-50 → `-1` |

⇒ **换算：度/秒 = RPM × 6**（实测比值 5.3~5.6，差额来自起动加速）。
⇒ **别把速度当度/秒用** —— 设 50 转 1 秒是 **270 度**，不是 50 度。

> ⚠️ **符号语义**：+50 → 位置 **正**、`dir=+1`；-50 → 位置 **负**、`dir=-1` ⇒ 严格对称。
> ⇒ JHYY 侧直接沿用 VEX 的符号即可，**不要自己再翻一次**。

### 9.8 clang `-Os` 的**尾合并**（实测 2026-11-10）—— 对拍时的一个坑

A 路（clang `-Os`）会把 if/else 两个分支里**参数形状相同**的调用
**尾合并**成一个调用点（先选好实参，再统一 `bl`）：

```asm
    movw r2, =<"MOTOR MOVED">
    b    call
else:
    movw r2, =<"MOTOR DID NOT MOVE">
call:
    mov  r0, #1
    mov  r1, #1
    bl   jhyy_vex_display_puts
```

实测：源码里 `jhyy_vex_display_puts` 有 **4 处**调用，
A 路产物里只有 **2 个调用点**；B 路（我们的汇编，不做这个优化）仍是 4 个。

⇒ **对拍不能比「调用次数」**，要比
① 调用的**函数集合** ② 去掉尾合并项后的**调用顺序**。
（`spike/day3-cmp/build-all.sh` 的 ⑤.4 就是这么比的。）

### 10.1 堆的分配器：newlib 子集里**根本没有分配器**（实测 2026-11-09）

`nm` 全量扫 `stdlib_0.lib`：**没有** `malloc` / `free` / `calloc` / `realloc` / `sbrk`
—— 一个都没有（只有 `_malloc_trim_r` 这种弱残留，与 `malloc` 无关）。

⇒ **链这份 libc 的程序不能调用 `malloc`** —— 链期就报未定义符号，不是运行期失败。

唯一的堆原语是 `libv5rt.a(v5_startup.c.obj)` 里的 **`_sbrk`**（弱符号）。
反汇编（`.text._sbrk`，重定位为准）：

```
_sbrk(incr):
    if (break == 0) break = _heap_start;      # 首次调用才初始化
    old = break
    break = old + incr                        # 新 break
    if (break > _heap_end) { break = old; return -1; }   # 越界 ⇒ 回退并返回 -1
    return old                                # 返回本次拿到的块首地址
```

- `_heap_start` / `_heap_end` 由 `lscript.ld` 的 `.heap` 段给出（`_HEAP_SIZE` 默认 `0x100000`）。
- 实测（`spike/day0-lab`）：`_heap_end - _heap_start` = **0x100000**（1 MB 整）。
- `_sbrk(0)` = 只读当前 break（不改变状态）⇒ 可以安全地拿来"看堆剩多少"。

> ⚠️ **对 B 阶段的含义**（不是实验结论，是已测事实的直接推论）：
> JHYY 的 `mem` / `arena` **不能指望 libc 的 `malloc`** ——
> 要么在 `_sbrk` 上自己实现一个 bump allocator，要么完全不依赖堆。
> 这条属于**接口/设计**，按验收线 § 3.4 的旁路口径处理（本仓自己养，不回灌主仓）。
>
> ⚠️ **"堆有 1 MB" ≠ "1 MB 都可用"** —— 固件自己也可能已经从这段内存里拿过东西。
> **启动时到底还剩多少 = 实机问题**，见 § 13（探针 `spike/day0-lab` 测 `_sbrk(0)`）。
>
> ✅ **实机已测（§ 13.1）**：`_heap_end - _heap_start` = **1048576**（1 MB，与静态实测一致），
> **启动时可用堆 = 1048576**（**整块都是空的** ⇒ 固件没占），
> `_sbrk(4096)` **分配 + 写回 + 读回都成功**。
> ⇒ **堆是真能用的**；缺的只是**分配器** —— JHYY 侧得自己在 `_sbrk` 上做 bump allocator。

## 15. 拆 SDK 的办法（可复用）

```bash
arm-none-eabi-ar x libv5rt.a v5_startup.c.obj   # 抽出单个 .obj
arm-none-eabi-objdump -d --section=.boot v5_startup.c.obj   # 反汇编启动代码
arm-none-eabi-objdump -r --section=.boot v5_startup.c.obj   # 重定位 = 权威调用关系
arm-none-eabi-readelf -A <elf>                   # ARM 属性（ABI 判定）
arm-none-eabi-nm --size-sort -S <elf>            # 段/符号尺寸（内存预算）
```

> **重定位表是权威证据**：`.o` 里所有 `bl` 目标都显示为 `0`，
> 但 `-r` 会给出 `R_ARM_CALL <真实符号名>`。

**按值传参的 struct：两侧都要看**

```bash
arm-none-eabi-ar x libv5rt.a v5_apijump.c.obj     # 纯 C API 的跳表桩
arm-none-eabi-objdump -d --section=.text.vexDeviceVisionWhiteBalanceSet v5_apijump.c.obj
```

SDK 桩里能看到它**从哪个寄存器取** struct、**从哪个寄存器返回** struct ——
这是「固件那头要什么」的权威依据；调用方那头由 `scripts/measure-abi.sh` 量。

**量布局 / 量传参约定**

```bash
scripts/measure-abi.sh
```

把 `sizeof` / `alignof` / `offsetof` 编码成**全局数组的长度**，
`nm -S` 读回来的 size 就是测量值；同一脚本还反汇编调用点，看实参/返回值落在哪个寄存器。
